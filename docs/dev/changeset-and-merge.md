# 確認依頼と反映

`CLAUDE.md` から分けた。下に挙げた場所を触る前に読むこと (`CLAUDE.md` の「触る場所と、先に読むファイル」)。

## 確認依頼は変更の集まり

1つの改訂で規程と細則の両方を直す、というのが現実にある。別々の改訂版に分けると
確認依頼も別々になり、**片方だけ反映された状態が作れてしまう。**

- 対象は `pulls.targetFiles` (カンマ区切り) が本体。`prTargetFiles(pr)` で読む。
  この列を足す前の依頼は本文の `[target-file:...]` にしか対象を持たないため、
  そこへ落とす
- `prCreate` は1つでも配列でも受ける。**その改訂版に入っていない文書は拒否する**
  (作業コピーが無いと「何を反映するのか」が無い)
- 画面の反映先には、**この改訂版の文書を全部持っている版だけ**を出す。1つでも
  欠けた版に出すと、反映のときに作業コピーが見つからず落ちる

### `prMerge` の順序を崩してはならない

```
1. 全件のマージ結果を作り、全件が書き戻せることを確かめる
2. どれか1つでも駄目なら、何も変えずに中断する
3. そのあとで、まとめて書き戻す
```

**1件ずつ「検証して書く」を繰り返してはいけない。** 3件目で落ちたとき、1件目と
2件目だけ反映された状態が残り、確認を経ていない中途半端な正式版ができる。戻す
手立ても無い。`test/changeset.test.js` の「1件目も書き戻さない」がこれを固定して
いる（検証したその場で書き戻す形に変えると実際に落ちる）。

食い違いの選択は `{fileId: [...]}` で受ける。配列1本の古い形も通す
(`prChoiceMap_`)。通さないと、画面を直すまでのあいだ選んだのに反映されない。


## 反映先は main とは限らない

確認依頼は改訂版どうしでも出せる。`pulls.targetBranch` が反映先を指し、
`prTargetBranchFileId` がその版の作業コピーを返す。

**起点は文書ごとに持つ (`files.baseSha`)。** 改訂版は複数の文書を持てるので
(`branchAddFile`)、2つ目を足した時点では正式版が1つ目より進んでいることがある。
ブランチに1つだけ持たせていると、2つ目の起点が古すぎて「相手が消した」と読め、
**黙って消える**。`branches.baseSha` は、この列を足す前に作られた改訂版のための
落とし所として残してあるだけである。

パスがどの版のものかは `branchSplitPath_` が唯一の定義。`branchOfPath_` は
そこへ委ねるだけにしてある（以前は同じ判定を別実装で持っていた）。

**3つを見比べる起点 (`prMergeBase_`) は、両方の分かれ目のうち古いほうを使う。**
新しいほうを使うと、相手にまだ無い変更まで「相手が消した」と読め、黙って
消える。`test/phase2-integration.test.js` の「分かれ目が違う版どうしを見比べる」
がこれを固定している（起点の選び方を逆にすると、実際に条文が1つ消える）。

## 変わった箇所の要約 (`src/core/DiffSummary.js`)

確認依頼の先頭・知らせのメール・命令キューの `prPreview` に出す「変わった箇所」の箇条書き (やること #109)。
上長は差分の行を読まないので、行の差分 (`diffHtml`) を人の言葉にする。AI は使わず、決まった読み方で作る。

- **正規化の出力 (`Normalize.js`) には触れない。** 読むのは行の差分だけ。場所は直前の見出し (h1〜h3) と、段落の頭の
  印 (`第3条` / `1.` / `2 ` / `（2）` / `①` / `一、`) から決める。条の印が出たら項の印は捨て、見出しが出たら両方捨てる
- 削除と追加が並んだら1つの「変更」に組む (`diffPairs` と同じ考え)。抜粋は場所の印と重なる頭を外す (`第3条: 第3条 …` にしない)。
  印だけが変わったとき・片方が印だけのときは印ごと見せる。字が同じで装飾だけ違えば「装飾だけ」
- 表は行の中を見ない: 行の追加・削除を行数で、組みになった行の違うセルを数で言う。数式 (`data-formula`) の違いもセルの違いに数える。
  丸ごと足した・消した表は「追加 (N 行)」「削除 (N 行)」。表の名前は、直前の段落が `別表1` / `表2` で始まればそれ、Sheets は
  シートの名前、どちらでもなければ場所 (`第8条 の表`)
- 同じ場所に同じ種類が続けば1本にまとめる (`ほか N 段落`)。最大 8 本 (`DIFF_SUMMARY_MAX()`) で、超えたら最後に `ほか N か所`
- **見るのは起点 → 改訂版** (`prPreviewMerge` の `changeOps`)。画面の差分のタブは反映先 → 反映の結果なので、反映先が先に進めた
  ところも入る。要約に入れると「この依頼が何を変えるか」が読めなくなる。起点は見比べと同じく空白の扱いをそろえたもの
  (`prUpgradeBaseSpacing_`)
- メールは `prChangeSummary_` が作って `notifyPrCreated` / `notifyPrReviewRequested` に渡す (Notifier.gs は差分を読まない。
  知らせだけを読むテストの SOURCES に差分の道具を足させないため)。**作れなくても依頼は出せる** (握って空にする。知らせと同じ扱い)。
  頼む人が何人いても見比べは1回
- 要約の字に Git の言葉を使わない (`test/diff-summary.test.js` がファイルを見ている)
- テストは `test/diff-summary.test.js` (純粋な読み方)、`test/api/pr.test.js` (画面に渡す形・メールの本文・キュー)、
  `test/component/pulls.test.js` (札の位置と字のまま置くこと)

## 反映の理由と改訂履歴の表 (`src/core/Revision.gs` / `src/render/RevisionWriter.gs` / `src/api/Revision.gs`)

やること #111。反映のときに理由を一言もらい、文書ごとに「日付・反映した人・確認依頼の題名・理由」を並べ、
文書に表として書き出す。

- **理由は `pulls` の行に持つ** (`mergeReason`。反映した人は `mergedBy`。どちらも末尾に足した列。`docs/dev/ledger-schema.md`)。
  反映の記録 (`commits`) は文書ごとに1行で、書き戻すものが無い文書 (`same`) には行が無いため、確認依頼の単位で持つ
- `prMerge(number, choices, previewSha, reason)`。理由は鍵の中で、**何も書き戻さないうちに**確かめる (`prMergeReason_`。
  200字 `REVISION_REASON_MAX()` を超えたら断る・改行は空白にする)。空なら既定値 = 確認依頼の本文の、中身のある最初の1行
  (`prDefaultReason_`。末尾に足している `[target-file:...]` は人の字ではないので外す)。画面は `apiPrPreview` の `defaultReason` を欄に入れておく
- 反映の記録の文 (`反映: 確認依頼 #N 題名`) は変えない (`test/achievements.test.js` などがこの形を読む)
- 一覧 (`revisionHistory`) は、正式版への反映 (`prTargetBranch(pr) === 'main'`) で、その文書を対象に持つ (`prTargetFiles`) 依頼だけ。
  改訂版どうしの反映は入れない (正式版はまだ変わっていない)。作業コピーから開いても正式版に読み替える (`revisionMainFile_`)。
  **列を足す前の反映**は、反映した人を反映の記録を書いた人で読み (`反映: 確認依頼 #N ` で始まる記録の author)、理由は空のまま
  (本文の1行目で埋めると、その人が言っていない理由が残る)

### 改訂履歴の表の書き出し: 書いた直後に正式版の記録として残す

書き出すと正式版の中身が変わる。そのままだと「記録していない変更あり」になり、**次の反映が止まる**
(`prMergePlanOne_` が「記録していない変更があります」で断る)。3つの道を比べて、**書いた直後に `commitFile` で正式版の記録に
する**形にした (`revisionExport`)。

| 道 | 採らなかった理由 |
|---|---|
| 表に印を付けて、読み取り側で飛ばす | Docs の表は `data-` のような属性を持てない。印を「`改訂履歴` の見出しの直後の表」のような字で決めると、**その形をもう持っている文書の正規化の出力が変わり、過去の記録と食い違う** (CLAUDE.md「出力を変えてはいけない」)。飛ばした表は版管理から漏れ、人が直しても誰も気づかない |
| 新しい改訂版に書いて確認依頼にする | 台帳から機械的に作る表に承認の往復が要る。反映するとその反映が表に載っていないので、また書き出す依頼が要る (いつまでも追いつかない) |
| **書いてすぐ記録する** (採った) | 表も版管理の中に入り、差分にも履歴にも出る。記録の文は「改訂履歴の表を書き出しました」 |

確認依頼を経ない書き込みなので、次の守りを置いた。

- **管理者だけ** (`repoAssertAdmin_`)。画面のボタンを押せるかもサーバが決める (`apiRevisionHistory` の `canExport` / `exportBlocked`)
- **書く前に記録していない変更があれば断る** (`prRecordSpacingOnly_`。空白の扱いだけの違いは反映と同じく記録し直す)。人が正式版を
  直接いじった分を、表の書き出しの記録に紛れ込ませない
- 鍵 (`dbWithLock_`) の中で「見る → 書く → 記録する」。反映と同じく、そのあいだに別の反映が入らない
- 前に書き出したものと同じなら記録しない (`changed: false`)。空の記録を作らない
- **書き戻しの道具 (`writeBlocksToDoc` / `writeHtmlToSheet`) を使わない。** あちらは本文を丸ごと消して書き直す。
  Docs は末尾に `改訂履歴` の見出し (見出し2) と表を `appendParagraph` / `appendTable` で**足す**だけで、前に書き出した表
  (見出しの直後の表で、1行目が `日付 / 反映した人 / 確認依頼 / 理由`) があれば、その表だけを `removeChild` → `insertTable` で
  置き換える。**`body.clear()` はしない。** Sheets は `改訂履歴` のシートを作るか、そのシートだけを書き直す (書き出し専用なので
  `clear()` してよい。ほかのシートには触れない)
- **人が作った同じ名前の表・シートは置き換えずに断る** (1行目が書き出した見出しの行と違えば人のもの)
- 書く前に確かめる (`revisionTableProblems_`: 列数・空のセル・`htmlWriterValidate`)。セルは空にしない (理由が無ければ `—`)。
  実機の Docs は空の字を入れる操作を断る (`docs/dev/pitfalls.md`)
- Sheets のセルは先頭に `'` を付けて書く (日付の字が日付に、`=` 始まりが数式にならない)。Slides は断る
- 書き出しはいつも正式版に書く (作業コピーから押しても)。改訂版はあとで正式版から取り込めば同じ表を持つ。改訂版で表のあたりを
  直していると、反映のときに食い違いとして出る (どちらを残すか選べる)

テストは `test/revision.test.js` (理由・既定値・一覧の順・Docs の追記と置き換え・Sheets のシート・Slides と管理者以外で断る)。
Docs の疑似は同じファイルの `fakeDocumentApp` (段落・見出し・表の並びだけ。保存すると正規化 HTML にして `fake._docs` に入れる。
`clear` を持たない)。

## main の保護は API 層で行う

`assertNotProtected_` は `apiCommit` / `apiSaveMarkdown` から呼ぶ。
**`commitFile` そのものは変えない。** PR のマージは `commitFile` を直接呼ぶため、
人間の操作だけが止まる。

main を Docs で直接編集された場合の逃げ道が `apiStashMainDrift` である。
これが無いと「未コミットの main はマージも拒否される」ため行き止まりになる。
