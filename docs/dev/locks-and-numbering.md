# 番号と鍵

`CLAUDE.md` から分けた。下に挙げた場所を触る前に読むこと (`CLAUDE.md` の「触る場所と、先に読むファイル」)。

## 番号を振るときは鍵を取る

**番号を決めることと書くことを、1つの鍵の中で行う** (`dbAppendNumbered`)。分けると
ほぼ同時の2件が同じ番号を取る。そうなると一覧に同じ番号のものが2つ並び、
`dbFindOne` は先の1件しか返さないので、もう1件は見えるのに開けない幽霊になる。
Web アプリと1分ごとのトリガーが同じ表に書くので、鍵なしでは成立しない。

**鍵は `dbWithLock_` 以外で取らない。** `LockService` を直に呼ぶのはそこだけ。
コマンドキューは鍵を持ったまま命令を実行し、その中で番号を採るため、取り直す
作りだと取れるかどうかが `LockService` の入れ子の扱いに左右される。`dbLockDepth_`
で自分が持っているかを数え、持っているなら取りに行かない。

**鍵は短く持つ。** 画面からの登録は鍵を30秒まで待ち、待ちきれないと「混み合って
います」になる。1分ごとのキューが、命令が無くても鍵を取って Drive を覗き、命令を
まとめて1つの鍵で走らせ、1日1回の片付けまで鍵の中で走らせていたため、実機で
スプリントが作れなかった。キューは命令1件ごとに鍵を取り (`runCommandFileLocked_`)、
命令が無ければ取らない。Drive を何度も見に行く片付けは鍵の外で走らせ、書くところ
だけがそれぞれ鍵を取る。**関係の無い Drive の一覧や、時間のかかる処理を鍵の中に
相乗りさせない。** 逆に、二度走らせないための「処理済みか見る → 走らせる → 印を
付ける」は短く鍵の中に置く (命令1件ごと・フォルダを作るとき・1日1回の片付けを
受け持つ印。片付けの本体は印を付けてから鍵の外で走らせ、済みの印は終わってから付ける)。

**`test/fakegas.js` の `tryLock` は常に true を返す。** 疑似GASのほうが実機より
甘いので、鍵の有無はテストで差し替えて確かめる (`test/numbering.test.js`)。

**一度出した番号は二度出さない。** 表の中の最大値だけを見ると、消した番号が次の
ものに回る。行を消しても、それを指しているものは他に残る。確認依頼の本文の
`closes #7` がその例で、#7 を捨てて完全に消し、無関係な新しいやることが #7 を
受け取ると、**その確認依頼を反映した時点で身に覚えのないやることが完了になる。**
出した番号はスクリプトプロパティに覚えておき、表が空になっても戻さない。
覚え書きが失われても、表の中の最大値より小さくはならない。

そのうえで**消すときはぶら下がっているものも全部消す**。`issuePurge` が
やりとり・ToDo の結び付き・知らせの行き先・カード・変更の履歴まで消し、報告は消さずに
結び付きだけ外すのはこのため。**やることの行は最後に消す。** 先に消すと、
途中で落ちたときぶら下がりだけが残り、`issueGet` が通らなくなってもう一度
片付けることができない。

**知らせは本処理を巻き戻さない。** `noticeAdd` は番号を振るので混み合うと
投げられる。やりとりは先に保存されるため、そこで投げると「書き込みは済んで
いるのに失敗と出る」。人はもう一度書き込み、同じやりとりが2つ並ぶ。`notify`
と同じく例外を握って `null` を返す。

**「あるか見てから書く」も鍵の中に入れる。** `projectPlace` と `prPatchAdd` が
そう。分けると、ほぼ同時の2件が「まだ無い」と読んで両方書く。板に同じカードが
2枚並び、`projectMove` は先の1枚だけ動かすので、もう1枚は外す道が無くなる。

**`dbUpdate` / `dbDelete` も鍵の中で行う。** `dbUpdate` は読んだ時点の行の位置へ
1行丸ごと書き、`dbDelete` は行を詰める。並んで走ると1行ずれた別の行を上書きし、
上書きされた行は黙って失われる。そのぶん、鍵を持っている誰かが長く持つと画面の
書き換えも「混み合っています」で待たされる（番号を振る追加と同じ扱い）。

**中身 (`objects/`) を置くのは検査を通ってから。** 先に置くと、上限で断ったときや
鍵が取れなかったときに、どこからも参照されない中身が残る。
