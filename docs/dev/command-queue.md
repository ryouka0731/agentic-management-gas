# コマンドキュー

`CLAUDE.md` から分けた。下に挙げた場所を触る前に読むこと (`CLAUDE.md` の「触る場所と、先に読むファイル」)。

## コマンドキューの落とし穴

(元は「落とし穴」の項目)

- **コマンドキューは「処理済みへ移す」だけでは二度実行を防げない。** 命令は手元が
  Drive の同期フォルダに置いたもので、手元に実体が残っていると同期の都合で
  `queue/` に戻ってくる。実際に「やることを1つ作ったのに、同じものが番号違いで
  複数できた」という形で現れた。`commandAlreadyRan_` で処理済みフォルダを見て
  弾き、`agent.mjs` 側も結果を受け取ったら命令を消す
- **結果を書く前に処理済みへ移す。** 逆にすると、結果を書いた直後に実行が
  打ち切られた場合 (6分の上限など) 命令が `queue/` に残り、次の起動でもう一度走る
- **キューの置き場は、ゴミ箱に入っていたら作り直す** (`queueFolderLive_`)。Apps Script は
  ゴミ箱の中のフォルダも開けるので、開けるかだけを見ると命令がゴミ箱に置かれて誰も
  拾わない。`setupCommandQueue()` もゴミ箱の中の ID を返し続けた (実機で踏んだ)
- **キューは仕掛けた人の権限で回る** (`QUEUE_RUNNER`)。共有ドライブでその人が抜けると止まり、
  他人のトリガーは見えない。`processCommandQueue` が回った時刻 (`QUEUE_LAST_RUN`) を残し、設定の
  画面が1時間より前なら引き継ぎ方を出す (持ち主 = 共有ドライブでは管理者の役割の人が `setupCommandQueue()`
  を実行する。`assertOwner_` なので投稿者などの管理者には動かない)。仕掛けた時刻 (`QUEUE_RUNNER_AT`) も
  残し、新しいほうで決める (仕掛けた直後は回った時刻が無い)。回った時刻は置き場を開けてから書く。
  確かめの入口 (`debugVerify*`) は手で回したぶんを元に戻す。人のアドレスを
  含むので `apiSettings` は管理者にだけ返す
- **置いた人 (`by`) を権限に使うのは、管理者だけの命令 (`COMMAND_ADMIN_OPS()` = `oshiProfileSet`) だけ。** ほかは誰の見え方かを
  決めるだけ。管理者だけの命令は `COMMAND_PERSONAL_OPS()` にも入れて持ち主と最後に書いた人を見比べ (`commandPersonOf_`)、
  **Drive の拡張サービスが無くて見比べられないとき・Drive が最後に書いた人を返さないとき (見えない人) は決めない** (`strict`)。
  走らせたあと、処理済み (`queue-done/`) に移した命令ファイルの中身を `{id, op}` に書き換える (プロフィールの中身を共有している人に
  残さない。名前は二度実行しない印なので残す)。マイドライブでは命令ファイルの持ち主を移せるので、
  持ち主だけで決めると、管理者に持ち主を移したファイルで管理者になりすませる。断るのは `repoAssertAdmin_(what, by)`

## キューのついでに台帳の覚えを温める

`src/core/CacheWarm.gs` (`cacheWarmTick_`) と `src/core/Db.gs` の `dbWarm_`。テストは `test/cache-warm.test.js`。

**なぜ。** 台帳の読み取りは CacheService (スクリプトのキャッシュ) に 30分置いている (`docs/dev/ledger-schema.md`)。スクリプトの
キャッシュは使う人全員で共有なので、だれかが読めば全員の初回の表示が速くなる。けれど 30分だれも開かないと切れ、次に開いた人の
画面が表を1つずつシートから読み直す (1表 0.16〜0.8 秒)。裏で読み直しておけば、朝いちばんに開いた人も速い。

- **新しいトリガーは足さない。** 1分ごとの `processCommandQueue` の終わりに相乗りする (トリガーを2本にすると、仕掛け直し・
  引き継ぎ・止まったかの見張り (`QUEUE_LAST_RUN`) を2本ぶん持つことになる)
- **温めるのは台帳の読み取りの覚え (`DB:<表>:<版>`) だけ。** Drive の一覧 (`filesPresentInDrive_` など) や人ごとに違う覚え
  (`ACH_PEOPLE:` など) は温めない。トリガーは仕掛けた人 (持ち主) の権限で回るので、その人に見える物がほかの人に見える物とは
  限らない。台帳の中身は誰が読んでも同じなので、持ち主が読んで置いてよい
- **温める = シートから読み直して、今の版の名で置き直す** (`dbWarm_`)。`dbReadAll` はキャッシュにあればそれを返して期限を
  延ばさず、CacheService には期限だけを延ばす口が無い。**キャッシュの中身を置き直さない**のは、人が台帳のシートを直にいじった
  ぶんがいつまでも見えなくなるため (シートから読めば、今と同じく 30分で見える)。**版 (`DBV:<表>`) は置き直さない** (読んでいる
  あいだにほかの実行が書いて版を変えると、前の版に戻して書く前の中身を当ててしまう)。版が無いときだけ `dbReadAll` と同じく
  新しい版を作る。この実行の中で書いた表 (`dbTableDirty_`) は置かない
- **温めた印 `DBW:<表>` (1500 秒) が無い表だけ読む。1回に読むのは3表まで** (`CACHE_WARM_PER_RUN_()`)。印も本体も温めた回から
  数えるので、同じ分に切れる印は3つまで。印が切れた次の回 (1分あと) に温め直せば、本体 (1800 秒) が切れる前に間に合う。差の
  300 秒は1分ごとの回の5回ぶんで、温めを飛ばした回とトリガーの遅れの余裕 (飛ばした回が5回続けば、その表は前と同じく次に
  開いた人がシートから読むだけ)。テストで「差が5回ぶん以上」を固定している
- **温める表は `CACHE_WARM_TABLES_()` の 22 表。** 画面を開いた直後に読む表 (疑似GASで画面を本物のサーバにつないで開き、
  シートを読んだ表を数えた。2026-10-28) から、次を外した: `commits` (記録のたびに文書の数だけ増え、いちばん大きい。開いた直後に
  要るのは一部の画面だけ)・`change_log` (変更のたびに増える。履歴の画面で読む)・`usage` (画面を開いているあいだ1分ごとに書かれ、
  版がすぐ変わるので温めてもすぐ当たらなくなる)。開いた直後に読まない表 (`pull_patches` / `outbox` / `impediment_comments` /
  `outcomes_daily` / `goal_items` / `goal_links`) も入れない。表を足すときは、開いた直後に読むか・どれだけ大きくなるかを見て決める
- **命令があった回は温めない** (手元は結果を待っている。キューの返事を先にする)。1回の実行が 20 秒を超えていた回 (1日1回の
  片付けなど) も飛ばす (`CACHE_WARM_SKIP_AFTER_MS_()`)
- **温めは投げない。** 落ちた表にも印を置いて (25分あとにもう一度) その回はそこで止め、キューのトリガーは止めない (Sheets
  そのものが落ちているときに、残りの表で同じ失敗を重ねない。落ちた表が先頭にいつづけて、ほかの表を温められなくなることもない)
- **持ち主のスイッチ:** スクリプトプロパティ `CACHE_WARM_OFF` に何か入れると温めない (エディタの「プロジェクトの設定」から)。
  人ごとの設定 (`PREFS_SCHEMA()`) にはしない (チームで1つのトリガーの話なので)

### 1日の予算の見積もり

個人のアカウントは、トリガーの実行時間が**1日 90 分**まで。超えるとその日のトリガーが止まり、キューも温めも止まる。

| | 回数 / 日 | 1回 | 1日 |
|---|---|---|---|
| キューの空の回 (置き場を開く・一覧・時刻を書く) | 1440 | 1.7〜4.2 秒 (2026-10-28 に本番で 9 回測った `QUEUE_LAST_COST`。多くは 2 秒前後。配り直した直後の 1 回だけ 19 秒) | 40〜60 分 (多くは 50 分前後) |
| 温め (22 表 × 1日 約 55 回 = 約 1200 回の読み取り) | 約 400 回の実行に分かれる | 1表 0.16〜0.8 秒 (2026-10-22 に本番で測った `dbReadAll` の値。ほとんどの表は 0.2 秒前後) とキャッシュに置くぶん | 4〜16 分 (多くは 5 分前後) |
| 命令・1日1回の片付け・成果の数 | 使い方による | | 数分 |

合わせて **55〜65 分ほど**で、90 分に収まる。**大半は温めではなく、空の回そのもの** (Drive の置き場を開いて一覧する時間。温めを入れる前から
掛かっていた)。温めの実測は 1 表 0.3〜1.6 秒 (3 表で 1〜2 秒、印がそろっていて読まない回は 0.05 秒) で、1 日 7 分前後。
空の回が 3 秒を超えて続くようなら、温めを減らすより先にトリガーの間隔を 2 分にする方が効く (キューの返事が最長 2 分待ちになる)。**1回ごとの所要時間を
スクリプトプロパティ `QUEUE_LAST_COST` に残す** (`{"ms": 全体, "warmMs": 温め, "warmed": 温めた表の数, "ran": 命令の数}`。
最後の1回ぶんだけ)。`ms` × 1440 が 60 分に近づくようなら、温める表を減らすか `CACHE_WARM_OFF` で止める。
スクリプトプロパティへの書き込みは1回に2つ (`QUEUE_LAST_RUN` と `QUEUE_LAST_COST`) で、1日 約 2900 回 (個人のアカウントの
上限は 1日 5 万回)。
