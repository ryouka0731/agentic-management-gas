# 台帳の列と、数える表

`CLAUDE.md` から分けた。下に挙げた場所を触る前に読むこと (`CLAUDE.md` の「触る場所と、先に読むファイル」)。

## メタDBの列を触るとき

`DB_SCHEMA()` が唯一の列順の定義である。

- **列は必ず末尾に足す。** 途中に挿入すると、既に書かれている行を新しい順序で
  読むことになり、値が1つずつずれる（`dueDate` を途中に入れて実際に踏んだ）
- **列を足したら、既に書かれている行の空欄をどう扱うか決める。** `reviews` に
  `id` を足したとき、それ以前の行は空のままで名指しできず、直そうとすると
  「やりとりを指定してください」で止まった。読むたびに埋める
  (`reviewBackfillIds_`) 形にした
- `test/schema.test.js` が全テーブルの列と順序を固定している

`focus_sessions` (集中のしかた) は `id` を `dbAppendNumbered` で振る通し番号にしている。`who` は小文字のアドレス。
時刻の欄 (`startedAt` / `openedAt` / `provedAt` / `endedAt`) は Date で書く。やることを `issuePurge` で消すと一緒に消す。
`columnAtStart` は始めた時点のボードの置き場 (カードが無ければ `none`)。ボードの移し替えは履歴に残らないので、
「始めたあとに作業中へ動かした」をこれと今の置き場で確かめる。**列を足す前の行は空のままにし、空は「分からない」として
ボードの手を数えない** (埋め直すと、始める前から作業中だったカードが「始めた」になる)。

`oshi` / `oshi_images` (推し) は末尾に `charId` (自分のキャラの番号。人ごとに 1 から) を足した。**足す前の行は空のままで、
その人の1人目 (1) として読む** (`oshiCharIdOf_`。それまでは1人1キャラだった)。埋め直さず、その行を書き直したときに 1 が入る。
名前の行が無く絵の行だけの人 (前は名前を決めずに絵を入れられた) も、1人目がいるものとして読む (`oshiMineIds_`)。
`charId` は `oshiCharCreate_` が鍵の中で決め、出した最大をスクリプトプロパティ `OSHI_CHAR_HIGH:<アドレス>` に覚えて
**消した番号を次のキャラに回さない** (回すと、自分の設定 `oshi.char` が指していた消したキャラが新しいキャラにすり替わる)。
`id` は今までどおり表ごとの通し番号 (`dbAppendNumbered`)。
`oshi` の末尾の `profile` は自分のキャラのプロフィール (検査を通した JSON。`oshiProfileValid_`)。**足す前の行は空のままで、
プロフィール無しとして読む** (`oshiProfileParse_`。読めない・検査に通らない値も無いことにし、次に書き直すときに空にする)。
字数の上限 (40項目・200字) だけでは足りない。**JSON にすると膨らむ字がある** (制御文字や対の無いサロゲートは `\uXXXX` の6字。
上限いっぱいで 5万5千字を超え、`dbUpdate` が英語のまま落ちた)。制御文字 (改行・タブを除く) は検査で落とし、JSON にして
`OSHI_PROFILE_JSON_MAX()` (4万5千字) を超えるものはふつうの言葉で断る (`test/oshi-profile.test.js`)。
最初からいるキャラのプロフィールは台帳に置かない (`docs/dev/permissions.md`)。
`oshi` の末尾の `shared` は「みんなに公開する」の印 (`true` / 空)。**足す前の行は空のままで、公開していないとして読む**
(`oshiSharedOn_`。手で書いた `TRUE` も公開として読む)。書くのは `oshiSetShared_` だけで、鍵の中で本人のキャラか確かめてから `dbUpdate` で
その欄だけ書く (`dbUpdate` は渡した欄だけを書くので、名前やせりふを直しても印は残る)。公開したキャラの名指しは行の `id` (`'shared:<id>'`)。
行を消すと番号は二度出さないので、消したキャラの名指しが別のキャラにすり替わることはない。

`goals` / `goal_items` / `goal_links` (目標。既定はオフ) は `id` をどれも `dbAppendNumbered` / `dbAppendNumberedMany` で振る
表ごとの通し番号にしている (目標ごとに振ると `dbUpdate` / `dbDelete` が関係のない目標の項目を書き換える)。`who` は小文字のアドレス。
`period` は `2026H2` / `2026Q3` (年は年度)。区切り (`goals.period`) を変えても、立てた目標の期は変わらない。
`approvedAt` は承認し直しを待つあいだも残し、`status` が `submitted` で `approvedAt` があれば「承認のあとに直した」と読む
(列を足さずに済ませた)。`autoScore` は評価を付けたときの見立ての字 ('0.7' は Sheets が数として持つので、読むときは字にする)。
`goals.fyStart` は立てたときの年度の始まりの月 (末尾に足した。空の行はいまの設定で読む。`goalRangeOf_` だけが期の日付を出す)。
`goal_items.actual` は数を入れる項目の今の値、`checked` はできた印 (TRUE)。保存し直しても測り方が同じなら残す。
`goal_links` は項目とやることの結び付きで、「あるか見てから書く」ので鍵の中で足す (`goalLink_`)。目標を消すと項目と結び付きも消し、
やることを `issuePurge` で消すと結び付きも消す。目標の保存 (`goalSave_`) は目標・項目・結び付きを1つの鍵の中で書く。

`announcements` / `announcement_replies` (お知らせ・1問アンケート・案内。`src/core/Announcement.gs`) は、どちらも `id` を
`dbAppendNumbered` で振る表ごとの通し番号にしている。`announcements.kind` は `notice` / `poll` / `ad`、`options` はアンケートの
選択肢の JSON の配列 (手で `a|b` と書いたものも読む。`announcementOptionsOf_`)、`startAt` / `endAt` は東京の `yyyy-MM-dd`
の字 (空は限りなし。Sheets が Date にしていても `plainDay` で日として読む)、`archivedAt` は終えた時刻 (空なら終えていない)。
`announcement_replies.who` は小文字のアドレス、`answer` は `''` (読んだ) / `'closed'` (閉じた) / 選んだ選択肢の字。
**1人1つのお知らせに1行だけ。** 「答えがあるか見てから書く」を1つの鍵の中で行い (`announcementReply_`)、2回目は書かずに
前の答えを返す。表の中身の誰が答えたかは画面に返さない (`docs/dev/permissions.md`)。

`priority` は**空欄を「ふつう」として読む**形にした (`issuePriority`)。埋め直さ
ないのは、空と「ふつう」を区別する意味が無く、書き戻すと更新の跡 (`updatedAt`)
が全件動いてしまうため。`reviews.id` のように名指しに使う列とは事情が違う。

**語彙は `ISSUE_PRIORITIES()` が唯一の定義**で、画面へは `apiIssuePriorities`
で渡す。画面側にも同じ並びを持っているが、あれは取れなかったときの控えである。
**足すときはサーバ側を直す。** 画面だけ足すと、選べるのに保存できない選択肢に
なる。知らない値は `issueUpdate` が弾く（通すと台帳に残り、読むたびに「ふつう」
へ倒れるので、直したつもりが直っていない状態になる）。


## 台帳の読み取りはキャッシュに置く。書くときは必ず `dbInvalidate_` を通す

**なぜ。** 本番で計ると、api* の時間の大半が台帳の読み取り (`dbReadAll`) だった。1回が 160〜800ms (issues 62行 36KB で
806ms、usage 401行 44KB で 281ms、小さい表でも 160〜200ms)。`apiOverview` 3598ms のうち読み取り7回で 2057ms、
`apiHomeSummary` 3753ms のうち8回で 1915ms、`apiOshiGet` 4599ms のうち8回で 2524ms。画面は開くと約30本の api* を
別々に呼ぶので、同じ表が何度も読まれていた (2026-10-22)。

`dbReadAll` (`src/core/Db.gs`) は2段で覚える。

| 段 | どこに | いつまで | 捨てるとき |
|---|---|---|---|
| 同じ実行の中 | グローバルの `DB_MEMO_` (表 → 行) | その実行のあいだ (Apps Script は呼び出しごとにグローバルを読み直す) | その表を書いたとき・**鍵を取ったとき** |
| ほかの実行とも | CacheService (スクリプトのキャッシュ) の `DB:<表>:<版>` | `DB_CACHE_SEC()` = 1800秒 (30分) | 版 `DBV:<表>` を変えたとき |

- **書く道はすべて `dbInvalidate_(表)` を通す。** `dbAppend` / `dbUpdateLocked_` / `dbUpdateManyLocked_` / `dbDeleteLocked_` (と、それを使う
  `dbAppendNumbered` / `dbAppendNumberedMany` / `dbUpdate` / `dbUpdateMany` / `dbDelete`) は中で呼ぶ。**Db.gs の外で台帳に直に書く所**も、
  書いたあとに呼んでいる: `usageRecord` (`Usage.gs`)・`noticeMarkRead` (`Notifier.gs`)・`reviewBackfillIdsLocked_`
  (`PullRequest.gs`)・`outcomesWrite_` (`Outcomes.gs`)。入れ物を作り直す `repoInit` は `dbInvalidateAll_()` を呼ぶ。
  **直に書く所を足すなら、必ず `dbInvalidate_` を通す** (探し方: `grep -rn "appendRow\|setValues\|deleteRow" src`)。
  通さないと、ほかの人の画面に 30分のあいだ古い中身が出る
- **版を変えるのは鍵の中なら鍵を放す直前、鍵の外ならすぐ** (`dbFlushInvalidate_`)。1回の操作で何行も書くとき1行ごとに
  キャッシュへ行かないため。放す前に変えるので、次に鍵を取った実行は必ず新しい版を見る。変える前に `SpreadsheetApp.flush()`
  で書いた中身を台帳へ送り切る (送る前に版を変えると、ほかの実行が新しい版の名で書く前の中身を置いてしまう)
- **同じ実行の中では、書いた直後の読み取りも新しい中身。** 同じ実行の中の覚えはすぐ捨て、版を変える前の表
  (`DB_DIRTY_`) はキャッシュを見ずに台帳を読む
- **鍵を取ったら同じ実行の中の覚えを捨てる。** 鍵の中の「読んで決めて書く」(番号・あるか見てから書く) は、ほかの実行が
  書いたあとの中身で決めないと同じものが2つになる (`docs/dev/locks-and-numbering.md`)。キャッシュの側は版で新しさが分かる
- **返すのはいつも写し** (行を作り直し、Date も作り直す)。呼び出し側が行に書き込んでも覚えは変わらない
- **Date は Date のまま返す。** JSON にすると字になるので `{"d": ミリ秒}` にして置き、読むときに戻す。列の並びも添え、
  列を足した新しいコードが古い形の覚えを読まないようにする
- **版が無い (初めて・追い出された) ときは新しい版を作ってから台帳を読む。** `'0'` のような決まった版に戻ると、
  前に追い出されたときに置いた古い中身が当たる
- **キャッシュが使えない・壊れている・置けないときは台帳を読む** (キャッシュで止めない)。版を置けないときは版の鍵を消す
  (読む側が新しい版を作る)。消すこともできないときだけ、古い版が 30分残りうる
- **1つの値は 100KB (バイト) まで** (`docs/dev/pitfalls.md`)。中身が `DB_CACHE_CHUNK_CHARS()` (25K 字。全部が3バイトの字でも
  75KB) を超えたら分けて置く: `DB:<表>:<版>` に `#<数>`、続きを `DB:<表>:<版>:<n>`。**超える表を置かない形にしなかったのは、
  usage が 400行で 44KB あり、180日ぶん (`USAGE_KEEP_DAYS`) たまると 100KB を超えるため** (いちばん重い表ほど効かなくなる)。
  分けても `DB_CACHE_MAX_CHUNKS()` (40 = 約100万字) を超える表は置かず、同じ実行の中の覚えだけで読む。続きが1つでも
  追い出されていれば台帳を読む
- **人が台帳のシートを直にいじったぶんは、30分まで古いまま見える** (以前は 300 秒。5分放置して開き直すと全部の表をシートから
  読み直して 1表 0.5 秒ほどかかり、開いた直後の api が軒並み遅かったので伸ばした。2026-10-27)。 管理者は設定の画面のチームの設定の
  「台帳の読み取りの覚え」(`apiCacheClear`。`repoAssertAdmin_`) か、エディタの `debugCacheClear()` ですぐ捨てられる
  (`docs/manual/admin.md`)。書き換えたあとに番号を振る・更新するのは鍵の中で台帳を直に読むので、そこは古くならない
  (`dbUpdateLocked_` / `dbDeleteLocked_` はシートを読む。`dbNextNumber_` は `dbReadAll` だが、鍵を取ったときに同じ実行の中の
  覚えを捨て、キャッシュも書いた実行が鍵の中で版を変えている。**直にいじった行だけは 30分のあいだ番号の数えに入らないことが
  あるが、出した番号はスクリプトプロパティにも覚えているので重ならない**)
- **裏で温める** (`dbWarm_`。1分ごとのキューのついでに `src/core/CacheWarm.gs` が呼ぶ)。本体 (`DB:<表>:<版>`、1800 秒) が
  切れる前に、温めた印 `DBW:<表>` (1500 秒) が切れた表をシートから読み直して今の版の名で置き直す (1回に3表まで)。キャッシュの
  中身を置き直すのではなくシートから読むので、直にいじったぶんが見えるまでの 30分は変わらない。版は置き直さない。どの表を温めるか・
  印と本体の長さの関係・1日の予算は `docs/dev/command-queue.md` の「キューのついでに台帳の覚えを温める」。**表を足したら、開いた
  直後に読む表かを見て `CACHE_WARM_TABLES_()` に入れるか決める**。テストが自分の CacheService の鍵を数えるときは、`DBW:` も
  台帳の覚えとして除く (`test/cowork-cache.js` の `keys()`)
- テストは `test/db-cache.test.js` と `test/cache-warm.test.js`。疑似GASの CacheService と読み取りの数え口は `docs/dev/testing.md`

## 数える表は、丸ごと読んで丸ごと書き戻す

`usageRecord` は `usage` の全行を読み、足し込んでから全行を書き戻す。**だから
行が増えたぶんがそのまま待ち時間になる。** 5400行で1回の記録が5400行の読み
書きになるのを実測した。1分ごと・タブごとに走るため、放っておくと実行時間の
上限に当たって数えられなくなる。

`USAGE_KEEP_DAYS()` (180日) より古い行は足し込みのついでに落とす。画面から
見られるのは直近90日までなので、その倍あれば足りる。**落としたら余った行を
`deleteRow` で消す。** 消さないと、書き戻した中身の下に古い行が残る。

**日が読めない行は落とさない。** 手で消されたセルは空になり、字のまま比べると
空はどの日付より小さいので「ずっと前の行」として黙って消える。`YYYY-MM-DD` の
形をしているものだけを判定の対象にする。

**同じまとめの中に同じ場所が2度入ることがある。** 足し先を `values` の長さから
数えると、まだ書いていない行を指してしまい、例外でそのまとめのぶんが黙って
失われていた（画面側は重なりを潰して送るので現れなかったが、`apiUsageRecord`
は画面からの値をそのまま受ける）。`addedAt` で足し先を別に持つ。

疑似GASの `Utilities.formatDate` は実機と同じく、時刻帯と書式に従って返す。
以前はミリ秒の字を返していて、日の区切りと期間の絞り込みは、テストごとに
差し替えないと何も検査されなかった。

## 成果の数 (`outcomes_daily`)

`src/core/Outcomes.gs`。日ごとの**チーム全体の数だけ**を置く。人の名前もアドレスも持たない
(設計: `docs/superpowers/specs/2026-10-21-motivation-review.md` の §7・§8)。日は東京の暦日 D。

| 列 | 数えるもの |
|---|---|
| `day` | `yyyy-MM-dd` (東京)。台帳からは Date で返るので `usageDayOf_` で読む |
| `moved` | D の始まりに開いていたやること・確認依頼のうち、D より前の最後の動きが D-7 日以前で、D に動きがあった数。初めての動き (作った日) は数えない。やることと、それに結び付いた確認依頼が両方動けば両方数える |
| `closedClean` | D に完了にしたやることのうち、その日の最後の完了から7日以内に開き直されていないもの |
| `mergedClean` | D に反映した確認依頼のうち、反映より前に差し戻しが1件も無かったもの |
| `reopened` | D に開き直したやること (同じやることは1日1件)。見張り |
| `overdue` | D の終わりに開いていて、期限 (**いまの**期限の欄。期限の書き換えの履歴は追わない) が D より前のやること。置き場に移したものは数えない。見張り |
| `activePeople` | D に何か1つ記録した人の数 (変更の履歴・やりとり・確認・記録・依頼・証跡・報告・その返事)。手元からの命令で書いた行は、命令を置いた人として数える |
| `busyErrors` | D に鍵が取れずに投げた数 (**上限の数**。下を見よ)。見張り |
| `timeoutErrors` | D に画面で時間切れになった操作の数。見張り |
| `fxOff` | 楽しさの層 (`fun.*` / `focus.*` / `oshi.*` / `ach.*` / `game.*` / `home.cards.game`) のどれかを自分の設定で `false` と書いた人の数。見張り |

「動き」は、やることなら変更の履歴 (`change_log` の `issue:N`)・やりとり・作った時刻、確認依頼なら出した時刻・確認・
元の改訂版への記録 (その時点で開いていた依頼にだけ付ける)・証跡・反映した時刻。**取り下げた確認依頼 (`state` が `closed`) は数えない**
(取り下げた時刻を持たないので、数えるといつまでも開いていることになり、同じ改訂版から出し直した依頼と1つの動きを2回数える)。開いていたかは完了・開き直しの履歴の最後で決め、履歴の無い古い行は `createdAt` と `closedAt` で決める。

- **7日あとで決まる数があるので、毎回直近8日を数え直して日ごとに上書きする** (`outcomesDaily_`)。8日たった日はもう動かない。
  同じ日の行は増やさない (上書き)。数え直しの途中で表を書き換えられても、次の日にもう一度数え直す
- **数えるのは鍵の外、書くのは短い鍵の中** (`outcomesWrite_`。取れなければ投げずに諦める。次の日に戻る)。
  `processCommandQueue` が1日1回の片付け (`housekeepArchiveDaily_`) のあとに `outcomesDailyOnce_` を呼ぶ。**片付けとは別の印**
  (`OUTCOMES_ON` = その日、受け持ちは `OUTCOMES_RUNNING`) で1日1回にし、片付けが済んだ日 (`ARCHIVE_HOUSEKEPT_ON` が今日) だけ走る。
  同じ印にすると、数えるところで時間切れになったとき片付けごとやり直しになる
- `busyErrors` は `dbWithLock_` が投げるとき (`onBusy` で黙って次に回すものは数えない) に、スクリプトプロパティ
  `OUTCOME_BUSY:<日>` に足す (`dbBusyNote_`)。**上限の数として読む。** 投げたものの中には、呼んだ側が握って画面に届かない
  もの (変更の履歴 `historyRecord_`・知らせ `noticeAdd`・使われ方 `usageRecord`・キューの中の書き込み) も入る。画面に届いた
  ぶんだけを数えるにはサーバで見分けられないので、こちらを選んだ。**鍵を取らずに足す**ので、ほぼ同時の2件は1件に数え漏れる
  こともある。14日より古い鍵は1日1回の片付けで消す
- **手元からの命令で書いた行は、トリガーを仕掛けた人 (持ち主) の名で残る。** そのまま数えると、持ち主1人が命令を回すだけで
  記録した人が増え、3人の守りを越えうる。`runCommandFileLocked_` が命令1件ごとに走った時間と置いた人をスクリプトプロパティ
  `OUTCOME_QUEUE:<日>` に覚え (`outcomesQueueNote_`)、その時間の中の持ち主の行は置いた人として数える (分からなければ数えない)。
  同じ時間に持ち主が画面で書いた行も置いた人に寄るが、命令は数秒で終わるので見込みの誤差とする。14日で消す
- `timeoutErrors` はサーバでは数えられない (打ち切られる)。画面の `call()` が時間切れの型 (`errorKindOf` の timeout) の失敗を
  使われ方の場所 `error:timeout` として数え、それを足す。**使われ方を止めた人 (チーム・本人) のぶんは入らない**。
  新しい api を作らずに既にある数え方に乗せた
- `fxOff` は数えた時点の数なので、きのうの行にだけ入れる。数え直しでは前の値を残す (空の日は「分からない」)
- **北極星 (止まっていたものが動き、7日のうちにきれいに終わった数) の結び付きはまだ持っていない。** 今あるのは moved と
  closedClean / mergedClean の別々の数だけで、同じ仕事かは見ていない
- 画面には週ごとの合計だけを出す (`apiOutcomes`。管理者だけ・3人に届かない週は null。`docs/dev/permissions.md`)
- 数え方は `test/outcomes.test.js` が1か月ぶんの台帳を手で数えた値と全部の日について突き合わせている

## 人ごとのスクリプトプロパティと 500KB

スクリプトプロパティは**全部で 500KB**、1つの値は 9KB まで。台帳に置かない人ごとの覚えはここに積もるので、足すときは
1人あたりの大きさを見積もる。いま人ごとに置くもの (目安):

| 鍵 | 中身 | 1人あたり |
|---|---|---|
| `ACH:<アドレス>` | 開いた日と取った実績の日 (63 個 × 鍵と日) | 約 2.4KB |
| `OSHI_CLEARED:<アドレス>` | クリアした日 | 数十バイト |
| `MYPREF:<アドレス>` | 自分の設定 | 数百バイト〜1KB |
| `STYLE:` / `CAL_PLANNED:` / `REWARD:` | 仕事のスタンス・予定・ご褒美 | それぞれ 9KB まで (ご褒美は 8000 バイトに収める) |
| `OSHI_PROFILE:<key>` とその続き | 最初からいるキャラのプロフィール (人ごとではなくキャラごと) | 1キャラ 最大 約 30KB (項目40 × 見出しと中身。続きは 20 個まで) |

**30人で 1人 5KB なら 150KB、最初からいるキャラ2人のプロフィールで 約 60KB。** 人ごとの値を足すときは1人 1KB 前後に収め、
大きくなりうるもの (一覧・記録) は台帳に置く。読むときに `getProperties()` を使うと全部 (最大 500KB) を1回で読むので、
何度も呼ばない (プロフィールの続きは版ごとに覚える)。
