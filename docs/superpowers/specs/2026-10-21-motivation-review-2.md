## B. 対象プロダクトの特定 (質問は要らない)

対象は番頭 (SoftBanto) と決まっているので、確認の質問はしない。前提は次のとおり。

- **使う人と業務:** 総務・人事。規程と細則を改訂し、確認と承認を通して正式版にする。月に数回で、毎日の道具ではない
- **技術:** Google Apps Script・Sheets の台帳。外部 API は使えない。AI は手元の Claude で、コマンドキューを経て数分遅れて動く
- **使わなくなる原因 [仮説。聞き取りで確かめる]:**
  - 間が空いて、どこまでやったか忘れる
  - 断り (「混み合っています」・英語の実行時エラー) で止まり、どうすればよいか分からない
  - Git の考え方 (版・反映) が分からない

**案は n8n / Zapier のようなワークフロー自動化の道具を想定して書かれている。** 番頭の「ワークフロー」は、改訂 → 確認 → 反映の流れのことである。
案の「ワークフローの定義・実行・再利用」の多くは番頭には当てはまらないので、下では番頭の言葉に読み替える。

### 1. 再開と次の一手 — **採る (最優先)**

- **根拠 [研究]:**
  - 中断したものは再開したくなる (Ghibellini & Meier 2025)
  - 実行意図 (Gollwitzer & Sheeran 2006)
- **番頭の今:** 「続きから」が無い。「あなたの番」と「改善のヒント」はあるが、理由が添えられていない [事実]
- **案から直す点:**
  - 「今日の発見」を毎日出す形は採らない。発見は「次の一手」の理由として、あるときだけ出す
  - 案は「価値がある時だけ」と書くが、価値の判定基準が無い。
    番頭では、台帳から言える事実 (期限・残り数・頼まれてからの日数) だけを理由にする
  - 「使うほど賢くなる AI」は、数人の操作の記録からは学べない。
    「前回と同じ手順」を見つけるのも、番頭の流れでは毎回ほぼ同じ (改訂 → 確認 → 反映) なので意味が薄い [仮説]

### 2. 戻せる安心 — **採る (案に足りなかった本命)**

**番頭には、反映したものを戻す道が無い** [事実]。`PullRequest.gs` のコメントに「元に戻す記録を別に作るしかない」とある。

失敗が取り返せないと、人は新しいことを試さない。
- [研究] チームの心理的安全性 (Edmondson 1999、要確認) は、もとはチームの対人関係の話である。道具の取り消しにそのまま当てはまるかは [仮説]
- 一方、UI の「取り消せること」が探索を促すことは、HCI の設計原則 (Nielsen の10原則「ユーザーの制御と自由」) で広く言われている。
  ただし実証研究ではない

採るもの:

- **前の版に戻す**
  - 反映した記録を選んで「この反映を取り消す確認依頼」を作る
  - 戻すのも、確認と承認を通す。正式版を道具が勝手に書き換えない
  - 中身は、前の版との差分を逆向きに当てるだけ。今の3つを見比べる反映 (`merge3`) にそのまま乗る
- **断りに「どうすればよいか」を添える**
  - 「混み合っています」・6分の上限・権限が無い・文書が消えた、などの断りを分類し、次にすることと、もう一度押してよいかを出す
  - 英語の実行時エラーは、そのまま出さない
- **案の「実験室」(ドライラン・サンプルデータ) は採らない。** 番頭の改訂版がそもそも実験室である
  - 正式版に触らずに直し、差分の見本を見て、反映する [事実]
  - 足りなかったのは戻す道だけである

### 3. 資産と感謝 — **一部を採る (感謝だけ)**

- **資産化:** 番頭の資産は文書そのもので、版管理されている。日報・下書きのひな形もある [事実]。
  プロンプトやワークフローの定義を新しく資産にする必要は、今の業務には無い
- **感謝 [研究]:** 予告なしの承認で成績が上がる (Bradler ら 2016)。
  採るのは、確認依頼を反映したとき、依頼した人が担当者へ一言返せることだけ。
  - 数えない
  - 集計しない
  - 送るのを促さない (10-14 仕様の③)
- **知識マップ・他部署の発見:** 採らない。対象が1つの部署で、文書は数十件。地図にするほどの量が無い [仮説]
- **「別部署で8時間の削減につながった」といった表示:** 採らない。推定の掛け算で、二重に数えやすく、検証できない

### 4. 自分の記録 — **小さく採る (日報の下書きの延長)**

- **成長グラフ (処理時間・手戻り率・エラー率を人ごとに):** 採らない
  - 人ごとの処理時間を持った時点で、本人だけの画面にしても台帳 (Sheets) は Drive を共有している人なら読める [事実]。監視の材料になる
  - 処理時間は仕事の重さで大きく変わるので、自分の過去と比べてもノイズが大きい [仮説]
- **ポートフォリオ:** 「今日片づけたもの」と日報へ写す仕組みが既にある [事実]。
  延長として、**週・月のまとめの下書き**を、本人が編集してから写せるようにする (保存しない・共有は本人がコピーで)
- **削減時間:** 出さない。案自身が「推定と実測を分ける」と書いているが、番頭には実測の手段が無い

## D. MVP (4つ + 小さな1つ)

### 1. 断りに次の一手を添える

- **課題:** 断られると止まる。もう一度押してよいのか分からず、同じものが2つできる (実際に起きた [事実])
- **解決:** サーバの断りを型に分け、画面は型から「次にすること」を出す
  - **型の例:**
    - `busy`: 混み合い。少し待って、もう一度押してよい
    - `timeout`: 6分の上限。途中まで済んでいるかもしれないので、一覧で確かめてから
    - `forbidden`: 権限が無い。誰に頼むか
    - `gone`: 文書が消えた。ゴミ箱から戻せる
    - `stale`: 開いたあとに直された。開き直す
    - `invalid`: 入力の誤り
  - **しくみ:** 断りの字は今のまま (`test/naming.test.js` の走査はそのまま効く)。字の先頭の決まった言い回しから型を引く表を `src/core/` に1つ置き、画面と同じ表を使う (両方にある関数として `test/ui-parity.test.js` に足す)
  - **英語の字:** 英語の実行時エラー (`Exceeded maximum execution time` など) は `timeout` などに読み替える
- **画面:** 今の帯 (`failSnack` / `failInto`) の下に1行「次にすること」と、型によって [もう一度] ボタン
  - [もう一度] は `busy` だけに出す
  - `timeout` には出さない (二重に作るため)
- **受け入れ条件:**
  - 今ある全部の `new Error` の字が、どれかの型に当たる (テストで走査する)
  - 当たらない字はテストで落とす
- **工数:** 2〜3日。前提は、断りの字を変えないこと

### 2. 続きから

1つ目の検証の §5〜7 のとおり。

- `apiResume` / `apiResumeMark`
- `RESUME:<email>` に「最後に開いたもの」を1件だけ覚える

**工数:** 2日

### 3. 前の版に戻す

- **課題:** 反映を取り消せないので、試すのが怖い
- **解決:**
  1. 文書の履歴で、反映の記録に [この反映を取り消す] を付ける
  2. 押すと、「取り消し」の改訂版と確認依頼を作る。中身は、その反映の前後の差分を逆向きに当てたもの
  3. あとの反映と重なる所は、今の食い違いの選び方で解く
  4. 承認されたら、今の `prMerge` で反映する
  - **新しい書き戻しの道は作らない。**「正式版を直接書き換えない」と `prMerge` の順序の約束を、そのまま守るため
- **受け入れ条件:**
  - 取り消したあとの正式版が、取り消した反映の直前と同じになる
  - 間に別の反映があった場合は、その変更が残る (`test/phase2-integration.test.js` に足す)
- **工数:** 3〜4日。食い違いの解き方は今の仕組みを使う前提

- **工数:** 2〜3日

## E. 技術設計 (案の表を、番頭の作りに読み替える)

**案の6つの表は、どれもそのままは作らない。**

| 案の表 | 番頭での扱い |
|---|---|
| `workflow_templates` / `knowledge_assets` | 文書とひな形が既にある |
| `workflow_template_usage` | 使われた回数は数えない |
| `improvement_metrics` | 人ごとの基準値は持たず、`outcomes_daily` にチーム全体だけ |
| `suggestions` | 理由は毎回台帳から計算し、保存しない |
| `feedback` | 第2段階の「ありがとう」で新しい表を作る |

**足すもの:**

- **断りの型の表:** `src/core/ErrorKind.js` (純粋な関数。画面にも同じ写し)
- **取り消しの確認依頼:**
  - `pulls` の末尾に `revertOf` (取り消した確認依頼の番号) を足す
  - `DB_SCHEMA()` の末尾に足し、`test/schema.test.js` を直す
  - 既存の行は空のまま (取り消しではない) と読む
- **権限:**
  - 取り消しの確認依頼は、改訂版を作れる人なら誰でも作れる (今の改訂版と同じ)
  - 反映は今の承認の決まり (差し戻しが残る間は反映しない) のまま
- **監査:** 取り消しの記録の文に「取り消し: 確認依頼 #N」と残る (変更の記録の文は人が読む。Git の言葉を使わない)
- **AI の提案 (第3段階):**
  - 手元の Claude への頼みごとに `suggest` を足す
  - 結果は「下書き」として、やることのやりとりに入れるだけ。何も変えない
  - 頼みごとの動詞を足すときは「手元で何が起きるか」を先に書く (`docs/dev/outbox-and-patches.md`)
- **テスト:**
  - 断りの全走査 (型に当たらない字を落とす)
  - 取り消しの通しのテスト (`test/e2e/`: 反映 → 取り消し → 承認 → 元どおり)
  - 計測の手計算との突き合わせ

## H. 最終提案

**「止まらない番頭」: 断られても次が分かり、間が空いても続きが分かり、反映しても戻せる。**

中身は MVP の 1〜3 (断りに次の一手・続きから・前の版に戻す) と、その効果を見る計測で、全部で 10〜12日である。

ほかの案より優れている理由:

1. **番頭で実際に起きた問題を直接減らす** [事実]
   - 断られて止まった
   - 同じものが2つできた
   - 反映を戻せない
   - 間が空いて分からなくなる

   成長グラフや知識マップは、まだ起きていない問題への答えである
2. **使い続ける理由が「仕掛け」ではなく「安心」になる。** 継続は、期待どおりに役立ったかで決まる (期待確認モデル、要確認)。
   失敗しても戻せる・止まっても分かる、は全員に効く。演出のように、好きな人にだけ効くものとは違う [仮説]
3. **個人の監視につながる数を1つも増やさない。** 人ごとの時間・成績を持たない
4. **測れる。** 二重作成の件数・成功までの時間・北極星は台帳から数えられる。推定値を出さない
5. **楽しさの層 (演出・推し・診断・当たり) と両立する。** この土台の上に任意で乗せ、効果は §F で同じように測る
