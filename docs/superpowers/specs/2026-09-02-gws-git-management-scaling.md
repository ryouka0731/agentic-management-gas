# GWS Git-like 文書管理システム — 大規模版スケーリング設計構想

- **日付**: 2026-09-02
- **ステータス**: 構想 (将来参照用。PoC では実装しない)
- **想定規模**: 100〜1,000 ユーザー / 1,000〜10,000 ファイル
- **関連文書**: [PoC 設計仕様](./2026-09-02-gws-git-management-design.md)

---

## 0. この文書の位置づけ

PoC (10ファイル / 3ユーザー) の設計をそのまま全社展開すると、**必ず壊れる箇所が
いくつか存在する**。この文書は「どこが、なぜ、いつ壊れるか」と「そのときに何を
差し替えるか」を、実装前に記録しておくためのものである。

**重要な設計方針**: PoC 実装の時点で、後から差し替えが必要になる部分を
**インターフェースとして切っておく**。具体的には以下の 5 層である。

```
Db層        ← スプレッドシート実装 → シャーディング実装 に差し替え可能
ObjectStore ← 単一フォルダ実装     → シャーディング実装 に差し替え可能
Lock層      ← ScriptLock          → 粒度別ロック       に差し替え可能
Cache層     ← CacheService        → 多段キャッシュ     に差し替え可能
Auth層      ← Drive権限依存        → 自前ACL           に差し替え可能
```

この 5 つさえアダプタとして隔離しておけば、大規模化は**アプリケーションロジックを
書き換えずに**達成できる。PoC 実装時にこの境界を守ることが、この文書の
最大の実用的価値である。

## 1. PoC の前提が壊れる順序

規模を上げていったとき、どの順番で何が壊れるかを予測しておく。

| 規模の目安 | 最初に壊れるもの | 症状 |
|---|---|---|
| **〜50 ファイル / 〜10 人** | (壊れない) | PoC 設計のまま動く |
| **〜200 ファイル** | Wiki のファイル一覧 | `files` シート全読み込みが数秒かかる |
| **〜500 ファイル** | `objects/` フォルダ | フォルダ内ファイル数が増え、`getFilesByName` が遅くなる |
| **〜50 人同時** | `LockService` のグローバルロック | コミット時にロック待ちが頻発、タイムアウト |
| **〜100 人** | **権限モデル** | 全員にメタ DB の編集権限を与えている構造が破綻 |
| **〜1,000 ファイル** | `commits` シート | 数万行になり、`getValues()` が 6 分制限に迫る |
| **〜100 人 / 常時利用** | トリガー実行時間の日次上限 | バックグラウンド処理が日中に止まる |

**注目すべきは「権限モデル」が 100 人あたりで壊れること。** これは性能問題では
なくセキュリティ問題であり、対症療法では解決できない。§4 で詳述する。

## 2. ストレージ層のスケーリング

### 2.1 `objects/` のシャーディング — Git と同じ解法

Drive の 1 フォルダあたりのアイテム数には上限があり (執筆時点で概ね 50 万件)、
上限に達する前から `getFilesByName()` の応答が劣化する。

**対策は Git がまさに採っている手法をそのまま使う**: SHA の先頭 2 文字で
サブフォルダに分割する。

```
.git/objects/
├── 0a/
│   └── 0a3f8b...html
├── 1c/
│   └── 1c9e21...html
└── ff/
    └── ffab04...html
```

これで 1 フォルダあたりのファイル数が 1/256 になる。さらに増えるなら 4 文字
(`0a/3f/0a3f8b...`) にすれば 1/65536 になる。

`ObjectStore` インターフェース側は変わらない:

```javascript
ObjectStore.put(sha, content)   // 内部でシャードパスを解決
ObjectStore.get(sha)
ObjectStore.exists(sha)
```

**PoC 実装時点でこのインターフェースを守っておけば、実装差し替えだけで済む。**

### 2.2 メタ DB のシャーディング

Google スプレッドシートは 1 ファイルあたり概ね 1,000 万セルの上限を持つが、
実用上の問題はそれよりずっと手前で起きる。**`getValues()` は行数に比例して
遅くなる**ため、数万行のシートを毎リクエスト全読みする設計は成立しない。

#### 対策 A: 時系列シャーディング (`commits` に適用)

`commits` は**追記専用 (append-only)** であり、古い行はほぼ読まれない。
年月でシートを分割する。

```
repo-db-2026 (スプレッドシート)
├── commits_2026_01
├── commits_2026_02
└── commits_2026_03
```

さらに「直近 N 件」を別の `commits_recent` シートに二重書きしておくと、
一覧表示は常に 1 シートの読み込みで済む。

#### 対策 B: インデックスシート

`branches` / `files` のような**現在の状態を持つテーブル**は行数が
ファイル数・ブランチ数に比例するだけなので、シャーディングより
**インデックス + 部分読み込み**が有効。

```
files_index シート:
  fileId → 格納シート名 + 行番号
```

`getRange(row, 1, 1, numCols).getValues()` で 1 行だけ読めば、
全読みを避けられる。

#### 対策 C: DB スプレッドシートの分割

最終的には、テーブルごとに別のスプレッドシートファイルに分ける。

```
repo-db-commits   (スプレッドシート)
repo-db-branches  (スプレッドシート)
repo-db-issues    (スプレッドシート)
```

分割すると**書き込みロックの競合も分離される**という副次的な利点がある
(§6 参照)。

### 2.3 いつ差し替えるべきか

| 指標 | 閾値 | 実施する対策 |
|---|---|---|
| `objects/` のファイル数 | 10,000 | §2.1 シャーディング |
| `commits` の行数 | 20,000 | §2.2 対策A + B |
| DB 書き込みのロック待ち | 平均 1 秒超 | §2.2 対策C |

## 3. 実行時間とクォータ

### 3.1 GAS の主要な制限 (執筆時点)

| 項目 | Google Workspace アカウント |
|---|---|
| スクリプト実行時間 | 6 分 / 実行 |
| 同時実行数 | 30 / ユーザー |
| トリガー総実行時間 | 6 時間 / 日 |
| トリガー数 | 20 / スクリプト / ユーザー |
| メール送信先 | 1,500 件 / 日 |
| `PropertiesService` | 1 値あたり 9KB、ストア全体 500KB |
| `CacheService` | 1 キーあたり 100KB、TTL 最大 6 時間 |

**これらの値は Google 側の変更対象である。実装前に公式ドキュメントで
再確認すること。**

### 3.2 6 分制限への対策 — 継続トークンパターン

大規模化すると、以下の処理が 6 分に収まらなくなる:

- 全ファイルの一括再インデックス
- 大量ファイルへのブランチ作成 (`makeCopy` の連続実行)
- 全文検索インデックスの再構築

対策は**チャンク処理 + 継続トリガー**である。

```javascript
function processBatch() {
  const state = loadState();               // PropertiesService から継続位置を復元
  const deadline = Date.now() + 4.5 * 60 * 1000;  // 6分より余裕を持たせる

  while (state.cursor < state.total && Date.now() < deadline) {
    processOne(state.items[state.cursor]);
    state.cursor++;
  }

  saveState(state);

  if (state.cursor < state.total) {
    // 自分自身を1分後に再スケジュール
    ScriptApp.newTrigger('processBatch').timeBased().after(60 * 1000).create();
  } else {
    cleanupTriggers();                     // 完了したらトリガーを必ず削除
  }
}
```

**重要**: トリガー数の上限は 20 件である。`cleanupTriggers()` を必ず実装し、
完了したトリガーを削除しないと、上限に達してシステム全体が停止する。
これは GAS の大規模運用で最も頻繁に踏まれる罠である。

### 3.3 トリガー総実行時間 (6時間/日) への対策

100 人が常時利用する規模では、バックグラウンド処理を「必要なときだけ」
動かす設計が必須になる。

| やってはいけない設計 | 代わりに |
|---|---|
| 5 分ごとの全ファイル同期ジョブ | **ライブキャスト方式** (PoC 設計 §4.2) — 描画時にのみ変換 |
| 定期的な全文検索インデックス再構築 | コミット時に**差分だけ**インデックス更新 |
| 全ユーザーへの定期通知バッチ | イベント発生時にのみ送信 |

**PoC で採用したライブキャスト方式 (キャッシュキーに `lastUpdated` を含める)
は、実は大規模化に対して最も効く設計判断である。** 同期ジョブが一切不要
だからである。この設計は規模が上がっても変えなくてよい。

## 4. 権限モデルの転換 — 最重要の課題

### 4.1 なぜ PoC の権限モデルが破綻するか

PoC では Web App を「**アクセスしているユーザーとして実行**」で公開する。
この方式には構造的な問題がある:

```
ユーザーとして実行
  → メタDB スプレッドシートへの書き込みが「そのユーザー権限」で行われる
  → 全ユーザーにメタDB の編集権限を与える必要がある
  → 誰でもスプレッドシートを直接開いて commits / branches を改竄できる
```

3 人の PoC なら許容できるが、**100 人規模では版管理システムの信頼性が
根本から失われる。** 「誰でも履歴を書き換えられる版管理システム」は
版管理システムではない。

### 4.2 大規模版の権限モデル

Web App を「**自分 (デプロイした管理者) として実行**」に切り替え、
**アクセス制御を自前で実装する。**

```
[ユーザー] → Web App (管理者権限で実行)
                │
                ├─ Session.getActiveUser().getEmail() で本人を特定
                │
                ├─ ACL チェック (自前実装)
                │     ├─ このユーザーはこのファイルを読めるか?
                │     └─ このユーザーはこのブランチにコミットできるか?
                │
                └─ 許可された操作のみ実行
```

これにより:

- **メタ DB はユーザーに直接公開されない** (管理者のみがアクセス権を持つ)
- 履歴の改竄が構造的に不可能になる
- 「誰が何をできるか」を細かく制御できる (Git のブランチ保護に相当)

### 4.3 ACL の設計

```
acl シート:
  principal       | resource          | permission
  ----------------|-------------------|------------
  someone@ex.com  | file:<fileId>     | read
  someone@ex.com  | branch:feat-*     | write
  legal-team      | branch:main       | approve
  *               | file:*            | read
```

- `principal` はメールアドレスまたはグループ名
- `resource` はワイルドカードを許すが、**照合はアンカー付き正規表現に
  変換して行う** (glob をそのまま使うと `branch:main` が意図せず
  マッチする危険がある)
- **グループの解決**には Directory API が必要になるが、Advanced Services が
  使えない制約下では、グループメンバーシップを `acl_groups` シートで
  手動管理する必要がある

### 4.4 ブランチ保護

Git のブランチ保護ルールに相当する機能を、大規模版では必須とする。

| ルール | 内容 |
|---|---|
| 直接コミット禁止 | `main` へは PR 経由でしかマージできない |
| 必須レビュー数 | マージには N 名以上の approve が必要 |
| 必須レビュアー | 特定のファイルには特定の承認者が必要 (CODEOWNERS 相当) |
| 自己承認禁止 | PR 作成者は自分の PR を承認できない |

`CODEOWNERS` に相当する機能は、規定文書の管理では特に価値が高い。
「就業規則の変更には法務部の承認が必須」といったルールを機械的に強制できる。

### 4.5 監査ログ

大規模運用では、性能よりも**説明責任**が重要になる場面がある。

```
audit_log シート:
  timestamp | actor | action | resource | result | detail
```

記録対象:

- すべての破壊的操作 (merge / branch 削除 / force 系操作)
- ACL の変更
- 権限拒否されたアクセス試行 (**これが最も重要**。不正アクセスの兆候を捉える)

`audit_log` は追記専用であり、時系列シャーディング (§2.2 対策A) の対象になる。

## 5. キャッシュ戦略の多段化

### 5.1 PoC の単一キャッシュの限界

`CacheService` は 1 キー 100KB、TTL 最大 6 時間という制約がある。
また `CacheService.getScriptCache()` はスクリプト全体で共有されるが、
容量は無制限ではない。100 人が 1,000 ファイルを閲覧する規模では、
キャッシュの追い出しが頻発してヒット率が落ちる。

### 5.1.1 実測値 (2026-09-02 / PoC環境)

A4 相当・約1,800文字・表1つ・画像1つの Google Docs 1件に対する計測:

| 経路 | 所要時間 |
|---|---|
| レンダリング (`DocumentApp` 走査) | **4,048 ms** |
| `CacheService` ヒット | **294 ms** |

**この数字が意味すること:**

- レンダリングは 1 文書あたり約 4 秒かかる。**100 文書を一括処理すると
  400 秒となり、6 分制限 (360秒) を超える。** 一覧表示でレンダリングを
  伴う設計は最初から成立しない
- 現設計 (一覧はメタDBから、本文は選択されたときだけレンダリング) は
  この制約に対して正しい
- キャッシュミス時に 4 秒待たされるため、`CacheService` の追い出しが
  頻発する規模では体感品質が大きく落ちる。**これが §5.2 の L2
  (Drive 上の永続キャッシュ) を必要とする根拠である**
- 逆に、コミット済み blob は `objects/` から読むだけでレンダリング不要な
  ため、履歴・差分表示は最初から高速である

### 5.2 多段キャッシュ

```
L1: CacheService (スクリプトキャッシュ)
      速い / 揮発する / 100KB制限 / TTL 6時間
      → 直近に閲覧されたファイルの HTML

L2: Drive 上の HTML キャッシュファイル
      .git/cache/<fileId>-<lastUpdatedMs>.html
      遅い / 永続する / サイズ制限が事実上ない
      → すべてのファイルの最新レンダリング結果

L3: レンダラ実行 (DocumentApp 走査)
      最も遅い (数秒) / 常に正しい
```

```
getLiveHtml(fileId):
  L1 ヒット → 返す
  L1 ミス → L2 ヒット → L1 に載せて返す
  L2 ミス → L3 実行 → L2 と L1 に載せて返す
```

L2 のキャッシュファイル名に `lastUpdatedMs` を含めるため、**古いキャッシュは
自然に参照されなくなる。** 週次のクリーンアップトリガーで、参照されなく
なったキャッシュファイルを削除する。

### 5.3 コミット済みバージョンのキャッシュ

**コミット済みの blob HTML は不変である。** したがって TTL を最大にでき、
かつ `objects/` から読むだけなのでレンダリング不要。ここは最初から高速である。

遅くなるのは**ライブ層 (未コミットの現在の状態)** のみ、という切り分けを
意識しておくと、最適化の対象を絞れる。

## 6. 同時実行制御

### 6.1 グローバルロックの限界

PoC では `LockService.getScriptLock()` を使うが、これは**スクリプト全体で
1 つのロック**である。100 人が同時にコミットすると、全員が 1 本の
ロックを奪い合い、待ち行列ができる。

### 6.2 粒度別ロック

論理的なロックをスプレッドシート上で管理し、リソース単位で排他する。

```
locks シート:
  resource        | holder          | acquiredAt | expiresAt
  ----------------|-----------------|------------|------------
  branch:main     | someone@ex.com  | ...        | ...
  file:<fileId>   | other@ex.com    | ...        | ...
```

```
acquireLock(resource):
  ScriptLock を短時間だけ取得 (locks シートの読み書きを排他)
    ├─ resource が未ロック or 期限切れ → 自分のロックを書き込んで成功
    └─ ロック中 → 失敗を返す
  ScriptLock を解放
```

**ScriptLock を保持するのは locks シートの読み書きの一瞬だけ**であり、
実際の重い処理 (レンダリング・マージ) の間はグローバルロックを持たない。
これにより異なるブランチへの操作が並列に走る。

### 6.3 楽観的並行制御

そもそもロックを取らず、**コミット時に HEAD が動いていないかを検証する**
方式のほうが、GAS のような環境には適している。

```
commit(branch, expectedHeadSha, newBlob):
  現在の headSha を読む
    ├─ expectedHeadSha と一致 → コミットして headSha を更新
    └─ 不一致 → 「HEAD が進んでいます。再読み込みしてください」エラー
```

Git の `non-fast-forward` 拒否と同じ考え方であり、ユーザーにとっても
理解しやすい。**大規模版ではこちらを主軸にすることを推奨する。**

## 7. 検索とインデックス

1,000 ファイル規模になると、「どこに何が書いてあるか分からない」という
問題が版管理そのものより重要になる。

### 7.1 全文検索インデックス

```
search_index シート:
  fileId | path | title | headings | bodyText(先頭N文字) | updatedAt
```

- **コミット時に、そのファイルの行だけを更新する** (全再構築はしない)
- 検索は `TextFinder` またはシート全読み + JS フィルタ
- 見出し (`<h1>`〜`<h6>`) を別カラムに持たせると、見出しヒットを
  優先表示できて実用性が上がる

### 7.2 Drive 検索との併用

`DriveApp.searchFiles()` で Drive 側の全文検索も利用できる。
自前インデックスは「正規化 HTML に対する検索」、Drive 検索は
「Google の検索エンジンによる検索」であり、性質が異なる。
両方を並べて出すのが実用的である。

## 8. 段階的な移行パス

一度に大規模版を作るのではなく、以下の順で必要になった時点で実施する。

| フェーズ | 契機 | 実施内容 | 見積 |
|---|---|---|---|
| **P0: PoC** | — | PoC 設計のまま | — |
| **P1: 小規模運用** | 20 人 / 100 ファイル | `objects/` シャーディング (§2.1)、楽観的並行制御 (§6.3) | 小 |
| **P2: 権限の厳格化** | 50 人 or 機密文書を扱う | **権限モデル転換 (§4)**、ACL、監査ログ、ブランチ保護 | **大** |
| **P3: 性能対応** | 500 ファイル | DB シャーディング (§2.2)、多段キャッシュ (§5.2) | 中 |
| **P4: 検索** | 500 ファイル | 全文検索インデックス (§7) | 中 |
| **P5: 全社展開** | 100 人以上 | 継続トリガー整備 (§3.2)、粒度別ロック (§6.2)、運用監視 | 中 |

**P2 が最大の山場であり、かつ最も後回しにされやすい。**
機密性のある文書を扱い始めた時点で、性能問題が出ていなくても
P2 を実施する必要がある。

## 9. GAS で成立しなくなる境界

正直に記録しておく。以下に該当する要求が出た場合、GAS 単独では
合理的に実装できない。

| 要求 | 理由 |
|---|---|
| **リアルタイム共同編集の版管理** | GAS には WebSocket も永続接続もない。ポーリングしかできず、トリガー実行時間の上限に当たる |
| **1 万ファイル以上の全文検索** | スプレッドシートベースのインデックスでは応答時間が実用域を外れる |
| **秒間数十リクエストの負荷** | 同時実行数 30/ユーザー、Web App の応答時間 (数百ms〜数秒) が壁になる |
| **バイナリファイルの版管理** | 画像・PDF の差分は取れない。「変わった / 変わらない」までが限界 |
| **文書内コメントの版管理** | `DocumentApp` からコメントを取得する API が存在しない |
| **1 コミット 10MB 超の文書** | `CacheService` / `PropertiesService` / 6 分制限が複合的に効いてくる |

これらが必要になった場合の選択肢は、社内規定の見直しを前提として:

1. **Advanced Google Services の解禁** — Drive API / Docs API が使えれば、
   構造化差分の精度が上がり、リビジョン取得も可能になる
2. **GCP プロジェクトとの連携** — Firestore をメタ DB にすれば、
   §2 と §6 の問題がまとめて解決する
3. **専用バックエンドの構築** — GAS を UI 層に留め、ロジックを外に出す

**ただし、この文書の想定範囲 (100〜1,000 ユーザー / 1,000〜10,000 ファイル) は、
GAS のみで到達可能である。** 上記の境界に当たるのは、それを超える要求が
出た場合に限られる。

## 10. PoC 実装時に必ず守るべきこと

大規模化を可能にするために、PoC 実装の時点で以下を守る。
**これらは PoC では何の役にも立たないが、後で差し替える自由を確保する。**

- [ ] `Db` / `ObjectStore` / `Lock` / `Cache` / `Auth` を**インターフェースとして定義**し、
      アプリケーションロジックから直接 `SpreadsheetApp` / `DriveApp` を呼ばない
- [ ] `ObjectStore` のパス解決を関数に閉じ込める (シャーディングを後入れ可能にする)
- [ ] コミット API に `expectedHeadSha` 引数を最初から持たせる (楽観的並行制御への移行を可能にする)
- [ ] すべての破壊的操作で `actor` (実行者メールアドレス) を記録する (監査ログへの移行を可能にする)
- [ ] 権限チェックを `Auth.can(actor, action, resource)` の 1 関数に集約する
      (PoC では常に `true` を返してよい。**呼び出し箇所を作っておくことが重要**)
- [ ] 長時間処理になりうる関数は、最初からカーソル (`{cursor, total}`) を
      引数と戻り値に持たせる (継続トリガー化を可能にする)

最後の項目以外はコストがほぼゼロであり、後から入れるコストは非常に大きい。
