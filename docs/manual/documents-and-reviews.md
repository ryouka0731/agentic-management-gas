# 文書と確認依頼

[手引きの目次](README.md)

文書を直して正式版に反映するまでの流れと、そのあいだに働く守り。考え方は [考え方](concepts.md) にある。

## 基本の流れ

1. 「文書」から文書を開く
2. 「この文書の改訂版」タブで **この文書の改訂版を作る** (正式版をコピーした作業用の版ができる)
3. 「本文」で **直す** に切り替えて書き換え、保存する。Docs / Sheets 本体を開いて直してもよい
4. 上の帯の **変更を記録** で、その時点を残す (一言を添える)
5. 「改訂中の版」から **確認を依頼** する
6. 承認されたら **正式版に反映する**

「改訂中の版」には、改訂版の一覧・「改訂版を作る」・記録していない変更を一度に記録する「まとめて記録」がある。

## 改訂版

- 改訂版は**複数の文書を持てる**。1つの改訂で規程と細則の両方を直すときは、同じ改訂版に文書を足す。
  別々の改訂版に分けると確認依頼も別々になり、片方だけ反映された状態が作れてしまう
- 起点 (どの記録からコピーしたか) は文書ごとに持つ。2つ目の文書を後から足しても、その時点の正式版が起点になる
- やることから改訂版を作ることもできる。名前は `issue-<番号>-<題名>` になる
- 途中の改訂版を土台に、さらに改訂版を作れる (長い改訂を分けて進めるため)
- 改訂版の名前は日本語でよい (例「見直し」)
- **改訂版を捨てられる**のは、作った本人か管理者だけ。捨てても台帳の行は残す (その改訂版から出た反映済みの
  確認依頼を後から開けるように)

## アプリの中で直す (Markdown)

改訂版の文書は、「本文」の「直す」で Markdown として書き換えられる。保存しても記録はされず、
「記録していない変更」になる (Docs で直した場合と同じ)。

| 書き方 | 意味 |
|---|---|
| `#` 〜 `######` | 見出し |
| 空行で区切った行 | 段落 |
| `- ` / `1. ` (入れ子は半角2スペース) | 箇条書き / 番号付き |
| GFM の表 (1行目を見出しとする) | 表 |
| `**強く**` / `*斜め*` / `<u>下線</u>` / `~~取り消し~~` | 装飾 (下線だけ Markdown に記法が無いので `<u>` を使う) |
| `[名前](URL)` | リンク |
| `![説明](sha:<sha>)` | 画像 (記録の中の画像を指す) |

書ける語彙は正規化 HTML に合わせて閉じてある。色・フォント・文字サイズは書けない (記録しないため)。

**上書きの前に、開いたときの指紋と比べる。** 「直す」を開いたあとに誰かが Docs で直していたら、保存を断る
(黙って上書きしない)。

## 正式版は直接なおせない

- 正式版の文書には「直す」が出ず、記録もできない (GitHub の branch protection にあたる)。変更は必ず確認依頼を通る
- 止めているのは画面と手元からの操作 (`apiCommit` / `apiSaveMarkdown`) で、反映の書き戻しは通る
- **Docs で正式版を直接なおされたとき**は、上の帯に「直接編集を退避」が出る。押すと、その中身を専用の記録として
  残す。これが無いと「記録していない正式版には反映できない」ため行き止まりになる

ただし Drive の権限で文書を開ける人は、Docs で正式版を直接なおせてしまう。塞ぎ方は [管理](admin.md#web-アプリの公開範囲) にある。

## 確認依頼

### 出す

「改訂中の版」から、反映先 (ふだんは正式版。改訂版どうしでもよい) と題名・本文を書いて出す。

- 出せるのは、**その改訂版の文書を全部持っている版**だけ。1つでも欠けた版には出せない
- 改訂版に入っていない文書は対象にできない
- Slides を含む確認依頼は断る (反映できないため)
- 本文に `closes #12` と書くと、反映したときにやること #12 が完了になり、反映した確認依頼の番号がそこに残る
- 確認する人を名指しすると、その人に知らせが届く。出した時点で、紐づいたやることのカードは「確認中」へ動く

### 画面

確認依頼を開くと、次のタブがある。承認と反映のボタンはタブの外にあり、どのタブからでも押せる。

| タブ | 内容 |
|---|---|
| やりとり | 本文と、承認・直してほしい・コメントの並び。`@名前` で人を名指しできる |
| 変更の記録 | この依頼に含まれる記録 |
| 差分 | 文書ごとの左右2列の差分 |
| コードの変更 | 添えたコードの差分 (下) |
| 手元への頼みごと | 手元の Claude に頼んだこと (下) |

### 承認

- 返し方は **承認 / 直してほしい / コメント** の3つ
- **出した本人は承認できない** (自己承認の禁止)。1人で試すときだけ、スクリプトプロパティ `ALLOW_SELF_APPROVE`
  で許す ([管理](admin.md#自己承認))
- 数えるのは**人ごとの最後の判断だけ**。一度「直してほしい」を返した人がそのままなら、ほかに承認があっても反映できない
- **承認は、承認した時点の中身にだけ効く。** そのあと改訂版の対象文書を記録したり、コードの差分を足し外ししたりすると、
  それまでの承認は数えなくなる (承認し直してもらう)。「直してほしい」は古くならない
- 反映には、有効な承認が1件以上要る
- 手元 (コマンドキュー) からは承認できない。キューは持ち主の権限で走り、常に自己承認になってしまうため

### 反映

「正式版に反映する」を押すと、まず下見が出る。

1. **3つを見比べる。** 起点 (両方の分かれ目のうち古いほう)・反映先・改訂版を見比べ、重ならない変更はそのまま合わせる
2. **同じ場所が両方で変わっていたら**「同じ場所が両方で変わっています」と出る。食い違いごとに、どちらを残すか
   (反映先 / 改訂版 / 両方) を選ぶ
3. **全部の文書が書き戻せることを確かめてから、まとめて書き戻す。** どれか1つでも駄目なら、何も変えずに止める。
   1件ずつ「確かめて書く」と、途中で落ちたときに一部だけ反映された正式版が残るため
4. 書き戻すと文書の fileId は変わらない。共有リンクも Drive の権限もそのまま
5. 紐づいたやることのカードは「完了」へ動き、`closes #N` のやることが閉じる

反映を断るのは、次のとき。

| 断る理由 | どうするか |
|---|---|
| 反映先に記録していない変更がある | 先に記録する (正式版なら「直接編集を退避」)。空白の扱いだけの違いは自動で記録し直す |
| 承認が足りない・「直してほしい」が残っている | 確認してもらう |
| 実体を取れない画像がある | 元のファイルで画像を貼り直す。書き戻すと画像が永久に失われるため |
| 下見のあとに中身が変わった | 下見をやり直す (見ていない食い違いの解き方で反映しないため) |
| 元の文書が消えている | 下を参照 |

書き戻す直前にも、反映先をもう一度見る。下見のあとに編集が入っていれば、自動で退避の記録を作ってから書き戻す。

**Sheets の書き戻しは、変わったセルだけを書く。** 読むのは表示値なので、全部を書き戻すと触っていないセルまで
丸めた値に置き換わる (3.14159 → 3.14)。シートを消してから書くこともしない (表示の書式が消えるため)。

### 取り下げ

- 確認依頼を**取り下げられる**のは、出した本人か管理者。反映済みのものは取り下げられない
- 取り下げても改訂版は捨てない (取り下げるのは「いま反映してよいか尋ねること」であって、直した中身ではない)
- 「確認中」へ動いたカードは「作業中」へ戻る
- **元の文書が Drive で消えた (ゴミ箱に入った) 確認依頼は、すぐ取り下げる。** 一覧を開いたとき・反映を押したとき・
  1日1回の片付けで確かめ、頼まれた人に理由を添えて知らせる。間違えて消して戻した場合は、出し直す

## 文書を外す・消えた文書

- 文書の登録を外すのは台帳の1行だけで、Drive の文書も記録も消えない (だから誰でも外せる)。
  改訂版が残っている文書と、作業コピーそのものは外せない
- **Drive で消された文書は一覧に出さない。** 台帳の行と記録は残すので、ゴミ箱から戻せばまた出る。元の文書が
  消えた作業コピーも出さない。中の文書が全部見えなくなった改訂版は、改訂版の一覧からも外す

## コードの差分を添える

確認依頼には、コードの差分を「証跡」として添えられる。規程 (Docs) と、それに合わせたコードを**1つの確認依頼**に
まとめるためのもの。総務は規程を読み、開発者はコードを読んで承認する。

- 添えるのは手元の道具から: `node agent.mjs patch <確認依頼の番号> <ファイル> [比べる先]`。差分を取るのは手元
  (`git diff`)。Apps Script では git のオブジェクトを読めないため
- 差分の本文は `.git/objects/` に置き、台帳には道のり・増えた行数・減った行数だけを持つ
- **反映しても、コードは書き換わらない。** 画面の断りにもそう出る。取り込むのは手元の git
- 文書が無く、コードの差分だけの確認依頼も出せる。そのときボタンの字は「承認を記録する」になる (承認1件は必要)
- 差分を足し外しすると、それまでの承認は数えなくなる

## 手元への頼みごと

確認依頼から、手元の Claude に頼みごとを置ける。番頭から手元へは Drive の同期しか経路が無いので、
**押すのではなく、手元が取りに来る形**である。寝ている機械は起きない。

| 頼みごと | 意味 | 置き方 |
|---|---|---|
| 差分を出して添える (`diff`) | 改訂版と比べる先の差分を作って添えてほしい | 画面から |
| 中身を読んで意見をもらう (`review`) | 中身を読んで意見を返してほしい | 画面から |
| 承認されたので取り込む (`merge`) | コードを取り込んでほしい | コードの差分が添えられた確認依頼を反映したとき自動で置かれる (手では置けない) |

- 頼めることは `OUTBOX_VERBS()` (`src/core/Outbox.gs`) に列挙してあり、引数も形を検査する。この表は Drive を共有
  している人なら手で書き換えられるので、自由な文字列にはしない
- 手元の道具は**頼みごとを実行しない**。中身を Claude に見せるところまでで止め、何をするかは人と Claude が決める
- 取ったまま24時間動かないものは、次に誰かが取りに来たとき「まだ誰も取っていない」に戻る

手元の側の使い方は [手元の道具](agent-kit.md#頼みごとを取りに来る) にある。

## 知らせ

確認依頼まわりの知らせは、画面の中 (鈴) とメールで届く。メールの件名は `[SoftBanto]` で始まる (受け取り側の
振り分けに使える。この接頭辞は変えない)。

| いつ | 誰に | メールの種類 (設定で止められる) |
|---|---|---|
| 確認依頼を出した | 出した本人 (控え) | 確認を頼まれた・確認依頼が出た |
| 確認を頼まれた | 確認する人として名指しされた人 | 確認を頼まれた・確認依頼が出た |
| 反映された | 出した本人 | 反映した・取り下げた |
| 取り下げられた (元の文書が消えて取り下げたときを含む) | 確認する人 | 反映した・取り下げた |
| やりとりで `@名前` と書かれた | 名指しされた人 | 名指しされた |

メールの種類ごとの止め方は [設定](settings.md) にある。知らせが送れなくても、本処理 (反映など) は巻き戻さない。

## ブラウザの AI に読ませる (Gemini in Chrome)

番頭そのものは外の AI を呼ばない (文書を外に送らない)。長い文書を要約したい・2つの版を比べたいときは、
**ブラウザ側の AI** を使う。

- デスクトップの Chrome (Windows / macOS / Chromebook Plus) では、ウィンドウ右上の「Gemini に相談」からサイドパネルが開き、
  **いま開いている頁の要約や、複数のタブをまとめた比較**ができる (日本では 2026 年 4 月から)。番頭の文書の全画面のリンク
  ([画面のめぐり方](screens.md)) で開いた頁や、Google ドキュメントそのものを開いて使える
- 読ませた中身は Google の AI に送られる。**人事・給与など社外に出せない文書は、会社の決まりに従って使うかどうかを決める**。
  番頭の設定では止められない (ブラウザの機能なので)
- 機能の名前や出し方は Chrome の更新で変わる。手引きが古くなっていたら、Chrome の「Gemini に相談」の説明を優先する
