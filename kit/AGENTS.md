# この道具の使い方 (Claude / Codex 向け)

あなたは、Google Workspace の文書に版管理を与える道具 **SoftBanto (通称 番頭)**
を、手元から操作しています。画面 (Web アプリ) を開かずに、やること・改訂版・
確認依頼を作れます。

**このフォルダで初めて動くなら、何か頼まれる前に `node agent.mjs setup` を
実行し、出た内容をそのまま利用者に見せてください。** 下ごしらえに要る3つの
場所と、いまどこまで出来ているかが出ます ([最初にやること](#最初にやること-このフォルダで初めて動くとき-まずこれ))。

## 仕組み

Apps Script API が使えない環境のため、**Drive 上のフォルダに命令のファイルを
置く**形で操作します。向こう側の時間主導トリガーが1分以内に拾って実行し、
結果のファイルを書き戻します。

```
手元 --(<id>.cmd.json)--> Drive の queue/ --(1分以内)--> 実行
手元 <--(<id>.result.json)-- Drive の queue/ <-----------+
```

**遅延は最大1分あります。** `agent` は結果が返るまで待つので、返ってこない
ときは向こう側の設定 (`setupCommandQueue()` の実行) か Drive の同期を疑って
ください。

## 最初にやること (このフォルダで初めて動くとき、まずこれ)

**何か頼まれる前に、いちばん最初に次を実行して、出た内容をそのまま利用者に
見せること。**

```
node agent.mjs setup
```

この道具に鍵もトークンも要らない代わりに、**人にしか取れない場所が3つ**
ある。`setup` は、その3つが何で、どこから取るのか、いまどこまで出来ているか
を出す。知らないまま `agent files` を叩くと「設定が見つかりません」で止まり、
次に何をすればよいか分からなくなる。

### 要る3つ

| | 何 | どこから取るか |
|---|---|---|
| 1 | 画面 (Web アプリ) のリンク | 道具を配っている人から渡されている。`https://script.google.com/macros/s/AKfycb.../exec` の形 |
| 2 | 命令の入れ先 (`.git/queue`) の手元でのパス | **画面**の右上の自分の顔 →「手元から動かす道具を落とす」。Drive の中での道のりが写せる形で出る |
| 3 | Apps Script のリンク | 最初の一人が `setupCommandQueue()` を実行するときだけ。済んでいれば要らない |

**この3つを当てないこと。** 向こう側 (Drive / Apps Script) には手元からは
触れないので、推測したパスは必ず外れる。分からないものは利用者に尋ねる。
尋ねるときは、上の表の「どこから取るか」をそのまま伝える。

### 書くところ

`agentkit.example.json` を `.agentkit.json` として写し、次を埋める。

- `queueDir` (必須) — 2 のパス
- `webAppUrl` (任意) — 1 のリンク。**人に決めてもらう操作を頼むときに渡す**
- `scriptUrl` (任意) — 3 のリンク

`webAppUrl` を書いておくと、承認のように人しかできない操作を頼むときに、
リンクをそのまま渡せる。毎回尋ねなくてよくなる。

### 通ったかの確かめ

```
node agent.mjs files
```

文書の一覧が返れば通っている。**返るまで最大1分かかる。** 向こうは1分ごとに
見に来る仕組みなので、すぐ返らないのは異常ではない。返ってこないときは、
向こう側で `setupCommandQueue()` が実行されているか、Drive for desktop が
同期しているかを疑う。

## 使う言葉

この道具は Git の言葉を使いません。人に見せる文言もこれに合わせてください。

| この道具 | Git でいうと |
|---|---|
| 正式版 | main |
| 改訂版 | ブランチ |
| 変更の記録 | コミット |
| 確認依頼 | プルリクエスト |
| 反映 | マージ |
| やること | Issue |

## よくある流れ

### 文書を直す

```sh
node agent.mjs files                      # 文書とその id を見る
node agent.mjs branch 見直し <mainFileId>  # 改訂版を作る
node agent.mjs read <workFileId> > body.md # 中身を Markdown で取る
# body.md を直す
cat body.md | node agent.mjs write <workFileId> -
node agent.mjs commit <workFileId> "第3条を改訂"
node agent.mjs pr "第3条の改訂" "根拠は…" 見直し <mainFileId>
```

### やることを作って進める

```sh
node agent.mjs issue "通勤手当の見直し" "4月から改定"
node agent.mjs issue-update 12 '{"assignee":"aoki@example.com","dueDate":"2026-10-31"}'
node agent.mjs issue-say 12 "根拠の通達を確認しました"
node agent.mjs issue-close 12
```

## コードの変更を添える

**この道具はコードの版管理をしません。** そこは git がやります。ここでできるのは
「何が変わったのかを人が画面で読んで、進めてよいと決める」ところだけです。

```sh
node agent.mjs patch <確認依頼の番号> <ファイル>          # 未記録のぶん
node agent.mjs patch <確認依頼の番号> <ファイル> main      # main との差
node agent.mjs patches <確認依頼の番号>                   # 添えたものを見る
node agent.mjs patch-rm <確認依頼の番号> <id>             # 外す
```

差分を取るのは**手元**です。向こう側 (Apps Script) では git のオブジェクトを
読めません (loose object は raw deflate で raw inflate が無く、packfile はさらに
delta チェーン)。だから `git diff` をこちらで走らせて、その結果を送ります。

### 添えても反映はされません

承認されても、コードは向こうで書き換わりません。**入れるのは手元の git です。**
向こうに残るのは「読んで進めてよいと決めた」記録だけです。

### 規程とコードを1つの確認依頼にまとめる

これがこの道具でしかできないことです。git は Google ドキュメントを持てず、
この道具はコードを持ちません。

1. 規程 (Google ドキュメント) を改訂版で直し、`commit` する
2. 同じ確認依頼に `patch` でコードの差分を添える
3. 総務は規程側を、開発者はコード側を読んで承認する
4. 反映すると**規程だけ**が書き換わる。コードは手元で `git merge` する

## 守ること

- **コードは反映されません。** 添えた差分は人が読んで決めるためのものです。
  実際に入れるのは手元の git です。「承認されたので反映されました」と
  言ってはいけません。言うなら「承認されたので、こちらで取り込みます」です
- **正式版 (main) は直接なおせません。** 直すときは必ず改訂版を作ってください。
  直接なおすと、誰がいつ何を変えたかが残りません
- **確認依頼の承認はできません。** 承認は人が画面で行う操作として残して
  あります。向こうのトリガーはアプリの持ち主の権限で走るため、ここから
  承認すると常に自己承認になってしまいます
- **色・フォント・文字サイズは版管理の対象外です。** 意味の変わらない
  見た目の調整は、記録しても差分に出ません
- **スライドは読むことと履歴の閲覧のみです。** 反映には対応していません
- 命令のフォルダは Drive を共有している人なら誰でも書けます。ここから
  できることは、向こう側が受け付ける操作だけに絞られています

## 結果の読み方

```json
{ "ok": true, "op": "commit", "result": { "sha": "9f8e..." }, "at": "..." }
```

`ok` が `false` なら `error` に理由が入ります。よくあるものは次のとおりです。

| 出るもの | 意味 |
|---|---|
| `正式版は直接なおせません` | 改訂版を作ってから直す |
| `同じ場所が両方で変わっています` | `pr-preview` で見てから `pr-merge` に選択を渡す |
| `記録していない変更があります` | 先に `commit` する |
| `反映できません` | 元に戻せない要素 (実体を取れない画像など) がある |
